# Architecture

## System overview

```text
Host Whisperer Studio
  normal developer form
  generates adapter + runtime
            |
            v
Northstar Admin
  developer reviews capabilities
  installs package
            |
            v
Northstar Market + installed plugin
  registers document.modelContext tools
            |
            v
ChatGPT in-app browser
  discovers and invokes tools
            |
            v
allowlisted page logic or narrow backend endpoints
```

The repository uses one React application and query-string routing to demonstrate three products. This is a demo convenience, not the intended production deployment topology.

## Application surfaces

### Host Whisperer

`/` explains the product. `/?view=integrate` stores a `SupportIntegration` profile in IndexedDB and renders the adapter generated by `generatedAdapter()`.

The target architecture uses ordinary UI here. It does not register WebMCP tools and does not depend on ChatGPT.

### Northstar Admin

`/?view=admin` simulates the target website's authenticated developer dashboard. It reviews the package and requested capabilities. Installing sets the demo installation state consumed by Northstar Market.

### Northstar Market

`/?view=shop` simulates the existing customer website. Its broken cart is deterministic. Before installation it shows only the native checkout error. After installation and after Checkout is attempted, it mounts `createHostWhispererRuntime()`.

### Escalation view

`/?view=incident#packet=...` decodes a bounded URL-fragment packet. The packet is not uploaded by the current demo. The view labels it untrusted evidence.

## Generated artifacts

The production build has two stages:

1. The main Vite build emits the React demonstration application.
2. `vite.runtime.config.ts` emits `dist/runtime/host-whisperer.js` as a standalone ESM library.

Studio generates `host-whisperer-adapter.js`, which imports that runtime and supplies application-specific callbacks.

```html
<script type="module" src="/support/host-whisperer-adapter.js"></script>
```

## Runtime configuration

`createHostWhispererRuntime(config)` accepts:

- Integration ID and public application name
- Exact allowed origin
- Provider hint for escalation context
- A safe-context callback
- Up to 20 diagnostics with unique IDs
- Up to 20 recovery actions with unique IDs
- An optional escalation destination

The runtime rejects an origin mismatch, empty tool sets, excessive tool counts, and duplicate IDs.

## Customer WebMCP tools

| Tool | Purpose | Mutation |
| --- | --- | --- |
| `get_support_context` | Create an incident and return sanitized, allowlisted page state | Incident state only |
| `run_support_diagnostics` | Run the developer-selected checks | No application mutation |
| `prepare_recovery` | Select an allowlisted action and expose its effects | No application mutation |
| `apply_recovery` | Run the prepared action after visible approval | Bounded application mutation |
| `verify_recovery` | Check whether the original symptom is gone | No application mutation |
| `prepare_developer_escalation` | Preview or create a customer-approved safe report | No infrastructure mutation |

Tool definitions are registered with `document.modelContext.registerTool()` and an abort signal. Destroying the runtime aborts registration and removes the Shadow DOM host.

## Incident state machine

```text
reported
   -> investigating
   -> diagnosed
   -> awaiting_approval
   -> repairing
   -> verifying
   -> recovered

Any failed repair or failed verification -> escalated
```

The incident ID binds subsequent calls to one active incident. A prepared action must match the approved action and can only run from `awaiting_approval`.

## Demo persistence

The demo uses same-origin browser storage so navigation between its simulated products preserves state:

| Storage | Key | Meaning |
| --- | --- | --- |
| IndexedDB | `host-whisperer-studio` | Latest integration profile |
| localStorage | `host-whisperer-northstar-bundle-ready` | Generated package sent to Admin |
| localStorage | `host-whisperer-northstar-installed` | Admin installed the package |
| localStorage | `northstar-demo-cart` | Cart schema and contents |

This is not a production package-delivery or deployment mechanism.

## Production hosting integration

Customer JavaScript must never contain provider credentials. If a playbook needs hosting or backend information, its handler calls a narrow, authenticated application endpoint:

```text
WebMCP tool callback
  -> same-site support endpoint
  -> authorization and policy check
  -> server-side provider integration
  -> sanitized result
```

Provider OAuth tokens or API keys remain server-side. Each endpoint should be tenant-scoped, rate-limited, auditable, and limited to one named diagnostic or recovery. High-blast-radius operations belong in an authenticated developer workflow, not the customer runtime.
